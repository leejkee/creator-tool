# 一图流 Web 编辑器：开发思路 Review 与需求草案

状态：方案评估，尚未进入实现。本文用于让后续 LLM 和开发者在同一口径下设计、拆任务与验收。现有三张安琪拉攻略、`guides/*.json`、`assets/` 和 Python 出图程序是迁移输入，不要求一次性替换，具体可以看我们初版工作目录`c:\user\31305\workspace\video-creator\wxq_anqila`，该目录下，我们做了llm读取用户笔记使用python代码合成图片的初尝试，并评估该方案为可复用工具开发方案，本目录为工具开发目录

## 1. 目标与边界

用户先给 LLM 一份攻略笔记初稿。LLM 整理内容、核对素材并生成可编辑的一图流草稿。用户在浏览器中直接点选任何文字、图片或装饰元素，逐项修改并实时预览。用户可以随时保存文档、查看修改历史、撤销操作，最后导出 PNG。LLM 能读取当前文档和近期修改记录，再根据用户指令精确修改指定元素。

核心交付物是**可编辑文档**；PNG 是它的一次导出。即使导出完成，文字、素材、裁剪、坐标和层级仍须可编辑。

首版按**本机单用户**设计。远程协作、多人同时编辑、账号权限、云端同步、移动端完整编辑和模板市场不属于首版范围。以后如需部署到多台机器，再重新评估服务端数据库和权限模型。

## 2. 当前项目的适配情况

- 现有 `guides/*.json` 已记录文案、图片名和部分坐标，适合作为导入源。
- 现有 `assets/` 保存原始图片，`assets/素材来源.json` 保存来源，能够迁入素材库。
- 现有图片中有 `heroes`、`eq` 等整排组件；这些组件的子项目前没有各自独立的编辑 ID。迁移到编辑器时，**每张棋子图、每个名字、每段说明都要得到稳定 ID**，才能实现逐项点选与 LLM 精确修改。
- 现有 Python 程序使用 Pillow 绘制。Web 首版可以保留它作结果对照，但 Web 预览和 PNG 导出应逐步共用同一套文档模型与渲染规则，避免两套排版逻辑长期分叉。

## 3. 总体结构建议

```text
笔记初稿 ──LLM整理──> 可编辑文档 ──浏览器编辑──> 新版本文档
                            │                    │
                            │                    └── 修改日志/撤销记录
                            ├── 素材库中的原图
                            └── 渲染器 ──> PNG / 预览
```

建议按四层理解，而不是把 PNG 当作数据库内容：

1. **文档层**：画布大小、页面、元素、层级、文本、图片引用、裁剪和样式。文档有稳定 ID 与递增版本号。
2. **素材层**：保留原始图片文件；记录元素名称、类型、尺寸、来源、哈希和使用情况。同一原图可在不同文档或同一文档多次引用。
3. **操作层**：手动编辑和 LLM 编辑都转成受校验的操作，写入修改日志，可撤销、重做和比较版本。
4. **渲染层**：编辑预览、缩略图与 PNG 导出尽量使用同一组坐标、字体、裁剪及层级规则。

## 4. SQLite 与图片文件

### 决策建议

本机单用户版本可以使用 SQLite 保存**文档元数据、素材索引、修改事件和版本快照**；原始 PNG/JPEG/WebP 继续保存在项目的素材目录。SQLite 并非存素材的必需条件，尤其在早期只有少量文档时，JSON 文件也能工作。但一旦要做素材搜索、引用关系、修改日志和版本查询，SQLite 的结构化查询更方便。

原图先存为文件，是为了继续沿用已有 `assets/`、方便人工检查和迁移、避免每次备份数据库都包含全部大图。这是本项目的工程取舍，**不是 SQLite 不能存图片**：SQLite 官方文档明确支持 BLOB，且小图片 BLOB 在某些条件下甚至可以比单独文件读取得更快。因此不应把“图片绝不能进数据库”写成硬规则。见 [SQLite 应用文件格式](https://sqlite.org/appfileformat.html) 与 [SQLite 对小 BLOB 的测试](https://www.sqlite.org/fasterthanfs.html)。

建议目录形态：

```text
workspace/
  editor.db                 # 文档、素材索引、事件与快照
  assets/originals/         # 不被裁剪覆盖的原图
  assets/thumbnails/        # 可重建的缩略图缓存
  exports/                  # 导出的 PNG 等成品
```

素材表至少包含：`asset_id`、显示名称、类别、相对文件路径、媒体类型、原始宽高、文件哈希、来源 URL、来源说明、创建时间。图片在文档中通过 `asset_id` 引用，不直接绑定可能改名的路径。相同文件哈希可提示重复素材；不同素材即使显示名称相同也不能共用 ID。删除素材时先检查引用，首版优先“归档”，避免旧文档变成缺图。

数据库文件和图片目录需要**一起备份/打包**；只复制 `editor.db` 不构成完整项目。若以后启用 SQLite WAL 模式，它允许读写并行，但数据库及其 WAL 文件要放在本机受支持的文件系统，不能把共享网络目录当作通用部署方案。见 [SQLite WAL 文档](https://www.sqlite.org/wal.html)。

### 候选数据表（概念层）

| 表 | 关键内容 |
| --- | --- |
| `documents` | 文档 ID、标题、画布尺寸、当前版本、状态、创建/更新时间 |
| `elements` 或 `document_snapshots` | 元素树及其属性；实现时可选规范化表或文档 JSON 快照 |
| `assets` | 素材 ID、名称、原图路径、尺寸、哈希、来源 |
| `operations` | 文档 ID、版本、操作者、操作类型、目标元素、变更前后值、时间 |
| `exports` | 文档版本、导出设置、文件路径、时间 |

不必一开始把所有元素属性拆成很多 SQL 列。单用户编辑器可以以**文档 JSON 快照 + 操作日志**为主，再用少量索引列满足列表与搜索；在真实查询需求明确后再拆表。

## 5. 编辑器的文档模型

一个文档可包含一页或多页。每页定义画布宽高和背景，元素按层级顺序绘制。第一版至少支持：文本、图片、矩形/圆角矩形、组合容器。元素通用字段：稳定 `id`、`type`、`parent_id`、`x/y`、`width/height`、`rotation`（首版可固定 0）、`visible`、`locked`、`z_index`。坐标一律按**导出画布的逻辑像素**保存；浏览器缩放只影响显示，不改变文档坐标。

文字元素另含：内容、字体族、字号、字重、颜色、对齐、行高、自动换行宽度。图片元素另含：`asset_id`、显示框尺寸、裁剪参数、填充模式、边框/圆角/透明度。组合容器只负责布局和层级；其中的图片及文字仍可单独选中。以后可加模板约束、网格吸附和可复用组件。

示意结构：

```json
{
  "documentId": "guide_001",
  "revision": 12,
  "canvas": { "width": 1600, "height": 2760, "background": "#101521" },
  "elements": [
    { "id": "hero_miyue_image", "type": "image", "assetId": "asset_miyue",
      "x": 76, "y": 721, "width": 432, "height": 142,
      "crop": { "x": 20, "y": 32, "width": 364, "height": 269 },
      "fit": "cover", "zIndex": 10 },
    { "id": "hero_miyue_label", "type": "text", "text": "主C · 优先觉醒",
      "x": 80, "y": 873, "width": 400, "height": 34, "zIndex": 11 }
  ]
}
```

这是模型示例，不是最终数据库 Schema。迁移时给已有视觉对象分配 ID，不把序号位置当永久身份；重排元素后 ID 不变。

## 6. Web UI 交互范围

### 首版必须有

- 左侧：文档列表、页面列表或素材入口；中间：可缩放画布；右侧：选中元素的属性面板。布局可随实现调整，功能需保留。
- 点选元素、拖动位置、改变宽高、编辑文字、改变颜色与字号、替换图片、调整层级、锁定/隐藏元素。
- 添加基础文本、图片和背景块；复制/删除元素；多选后移动或对齐。
- 自动保存或显式保存、未保存提示、撤销/重做；每次已提交操作形成可读日志。
- 使用当前文档版本导出 PNG；导出前显示尺寸与文件名，完成后可在 Web UI 下载。
- 素材库展示名称、缩略图、类别和来源；可以搜索并把素材拖到画布生成图片元素。

拖素材上画布时，应先出现放置预览；放手后才创建元素并记一条操作。拖动已有元素时，只在松开鼠标后记一次操作，而不是每个鼠标移动事件都写日志。素材被拖入时使用合理默认尺寸，不能在后台改变原图。

### 后续版本考虑

- 裁剪面板：可拖动裁剪框，也可精确输入起点 `x/y` 与 `width/height`。
- 裁剪格式刷：从一个图片元素复制裁剪参数，应用到一个或多个目标图片元素。
- 外观格式刷：独立复制显示框尺寸、圆角、边框、阴影等；不与裁剪参数混为一个按钮。
- 批量替换素材、模板、吸附与参考线、可复用样式、文档间复制元素、导出 PDF。
- LLM 可调用的文档读写接口与修改记录订阅。

## 7. 裁剪的精确定义

裁剪是**非破坏性操作**：原始图片永远保留。图片元素只保存“使用原图的哪一个矩形”。裁剪坐标基于原图的自然像素宽高，不基于页面缩放或图片显示框。可用 `crop = {x, y, width, height}` 描述。

- 默认：`x=0`、`y=0`；`width` 未填时取 `原图宽度 - x`，`height` 未填时取 `原图高度 - y`。这样满足“默认到达图片最大边界”。建议将“到边界”作为明确的动态值（例如 `null` 或 `to-edge`），而不是每次都固化成当前像素数。
- 校验：`x/y >= 0`、宽高必须大于 0，且裁剪矩形不得越过原图边界。非法输入给出原因，不静默截断。
- 替换素材：原裁剪值如对新图越界，提示用户选择“重置为全图”“按比例映射”或取消替换；不能悄悄裁掉内容。
- 显示框和裁剪框是两套坐标。若宽高比不同，默认使用 `cover` 填充；编辑器应让用户看到最终实际可见范围。`contain` 与 `stretch` 可作为显式选项，其中 `stretch` 会变形，应有明显提示。浏览器 Canvas 的 `drawImage` 支持指定原图裁剪矩形和目标显示矩形，足以实现该模型。见 [MDN drawImage](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage)。

**格式刷建议两种模式**：

1. **像素裁剪**：原样复制 `x/y/width/height`，适合尺寸一致的卡面。默认宽高到边界的语义对每张目标原图单独计算。越界目标跳过并汇总报告。
2. **比例裁剪**：把起点和宽高转换为源图宽高的比例，再映射到目标图，适合不同尺寸但构图相近的素材。

批量操作应在应用前展示目标数量与异常数；一键应用形成**一个可撤销的复合操作**，日志列出全部受影响元素与参数。不要为了“统一格式”生成覆盖原图的裁切副本；如需要缓存衍生图，缓存可删除重建。

## 8. PNG 导出与预览一致性

PNG 导出必须按文档逻辑画布尺寸生成，不受浏览器窗口缩放、设备像素比或滚动位置影响。先加载全部字体与图片，再按层级绘制，导出后核对图片尺寸；缺图时应失败并列出素材名，不能默默输出占位图。

建议将素材经应用自身的资源接口提供给画布，即在同源下加载。浏览器 Canvas 如果绘入未经跨域许可的远程图片，会成为受污染画布，`toBlob()` 等导出接口会失败；因此素材入库时下载到本地服务，再进行预览与导出。见 [MDN 跨域图片与 Canvas](https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/CORS_enabled_image) 和 [MDN toBlob](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob)。

验收时至少比较：文字换行、中文字体、图片裁剪、圆角、透明度、层级和画布边缘。若编辑器预览用 DOM、导出用另一套 Canvas 绘制，必须有对照测试；更理想是复用同一渲染模型。

## 9. 修改日志、撤销与 LLM 共享

用户操作和 LLM 操作必须经过同一个文档服务。每次**提交后的语义操作**记录：`operation_id`、`document_id`、`base_revision`、`new_revision`、`actor`（user/llm）、`type`、目标元素 ID、变更前值、变更后值、时间，以及可读摘要。例如：“用户把 `hero_miyue_label` 文案从 A 改为 B”。

拖动只在放手后记一次；连续输入可在短时间内合并为一次文字编辑；批量格式刷记一个事务，包含多个目标变更。撤销/重做也应形成可追踪的操作或明确的版本回退记录，不直接删旧日志。定期保存快照，避免每次打开文档都要重放全部历史。

LLM 至少需要这些**能力接口**，具体 URL 和协议留给实现阶段确定：

| 能力 | 输入与输出 |
| --- | --- |
| 读取文档 | 文档 ID → 当前版本、画布、元素树 |
| 查询元素 | 按 ID、文本、素材名或区域查找 → 候选元素及 ID |
| 读取修改 | 文档 ID、起始版本 → 操作列表、摘要、当前版本 |
| 预览 | 文档 ID、版本 → 可访问的缩略图或截图 |
| 应用修改 | 文档 ID、`base_revision`、一个或多个结构化操作 → 新版本、日志、校验结果 |
| 导出 | 文档 ID、版本、格式/尺寸 → 导出任务或文件 |

写接口应支持如 `set_text`、`move_element`、`resize_element`、`replace_asset`、`set_crop`、`set_style`、`add_element`、`delete_element` 等**有明确校验的操作**。LLM 不直接执行任意数据库 SQL 或整份 JSON 覆盖；批量编辑作为事务提交，要么全部成功，要么全部失败。若 `base_revision` 与当前版本不同，返回冲突和自该版本以来的修改，LLM 重新读取后再编辑，避免覆盖用户刚做的调整。

建议 LLM 在修改前读取目标文档和近期日志，修改后读取渲染预览与操作结果，并向用户说明具体改了哪些元素。日志记录事实，不把 LLM 的推测写成用户要求。

## 10. 分阶段开发与验收

### 阶段 A：文档底座和可编辑首版

定义文档模型、稳定元素 ID、素材引用、版本与保存方式；完成现有三张图的导入。实现画布点选、文字和基础样式编辑、拖动/缩放、素材拖入、保存、撤销、PNG 导出与修改日志。

验收：三张现有图导入后可逐项点选；修改芈月图“针对海月”的一行说明、移动一张棋子图并替换其素材后，保存重开仍保持结果；导出的 PNG 与画布预览一致；撤销可回到修改前。

### 阶段 B：精确裁剪与格式刷

加入裁剪面板、原图像素坐标、到边界默认值、批量格式刷、不同尺寸的像素/比例两种模式及越界报告。

验收：同一原图的两个引用可以使用不同裁剪；批量应用后原图文件和其它文档不变；异常目标不会被静默裁错；一次撤销可恢复整个批量操作。

### 阶段 C：LLM 接口与笔记初稿生成

开放受版本控制的读取、搜索、编辑、日志、预览与导出接口；增加从笔记生成草稿的工作流。LLM 负责内容整理与素材核对，编辑器负责验证与渲染。

验收：用户先在 Web UI 改一句话，LLM 随后能从日志看到这次修改并保留它；LLM 精确改另一元素时产生可读日志；旧版本请求被拒绝并返回冲突信息。

## 11. 需要在实施前确定的产品选择

以下不阻碍开始设计底座，但编码前应确定并记录：

1. 项目是否长期只在本机单用户使用？若要多人/远程访问，存储、同步和权限方案要升级。
2. 一份文档是单页一图流，还是允许多页？建议模型支持多页，首版 UI 可以只编辑单页。
3. 首版是否需要与原 Python 图片做到像素级一致？若需要，字体和裁剪算法要先锁定并做对照样本；若允许轻微差异，则以 Web 编辑器定稿输出为准。
4. 素材来源是否只用当前游戏卡面？若允许用户上传和第三方图片，素材类型、去重和来源记录要一起设计。
5. LLM 入口是本机 HTTP API、MCP 工具，还是先由应用内部调用？建议先实现稳定的文档服务接口，再包装具体入口。

## 12. 当前结论

方案可行。优先级应是**文档模型与导出一致性 > 稳定元素 ID 与日志 > 基础 Web 编辑 > 裁剪和格式刷 > LLM 接口**。SQLite 可用于结构化状态，原图以文件保存；裁剪保存为可撤销参数；LLM 和 Web UI 通过同一组带版本校验的操作修改文档。这些选择既支持当前三张攻略迁移，也为以后更多攻略和更细致的人工调整留出了空间。
